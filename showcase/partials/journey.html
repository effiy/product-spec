The full journey

This page follows acme-shop — the sample e-commerce spec — through every stage of the harness loop: from a blank canvas to a validated, critiqued, packaged, and observed spec. Each stage shows what fires under the hood, what artifact it produces, and what the honest limits of the check are.

THE CLOSED LOOP

One pipeline, one feedback loop

Raw ideas enter the pipeline as a Vision statement. They exit as a structured, traceable, validated, critiqued, and packaged spec. The loop does not end at Ship — telemetry reads the rig's health back, and critique findings flow back into recorded decisions via --apply-critique. --learn closes the outermost ring: spec → build → measure → learn.

STAGE 01

Define — Vision → BRD → PRD → Epic → Story

The product-spec skill runs a phased interview. For acme-shop, the PO answers questions about the north-star goal, the business objective, and the checkout feature area — and the skill builds the full five-layer hierarchy, each node traceable to its parent. Output lands entirely in docs/product/; the skill never writes outside that folder.

⚖️ Honest limit
  • The skill never sets status: approved on its own — that requires explicit PO sign-off with owner + date.
  • It never overwrites PO prose on --update — it flags affected nodes and asks first.
STAGE 02

Validate — scripts first, LLM judges

Validation runs in two passes. Deterministic scripts catch the structural failures that do not require judgment: orphaned nodes, missing acceptance criteria, broken ID traces, persona drift. The LLM layer then adds the judgment a script cannot: INVEST compliance, vague requirements, core-value drift, hidden duplicates. See the validation page for the full rule list.

STAGE 03

Critique — four lenses, one report

--validate tells you the spec is structurally sound. product-spec-critique tells you whether it is any good. Four specialist sub-agents work in parallel, each reading the same spec through a different lens, then a consolidator merges their findings into one report — deduplicated, severity-ranked, with a concrete fix per finding. Every finding cites a real ID:line.

🔁
Re-runs are cheap. Critique the same scope twice and it reuses prior work — no spec change means nothing is re-analysed; a --level bump alone only re-renders the voice without re-running sub-agents. Use --fresh to force a full rebuild. See critique and voice levels for the full contract.
⚖️ Honest limit
  • Critique never edits the spec — it writes one report, the spec stays untouched.
  • It is never a CI gate — it is opinionated and non-deterministic by design. --validate stays the reproducible gate.
  • A finding only becomes a recorded decision (DEC-<n>) if the PO confirms it — critique never writes to memory on its own.
STAGE 04

Ship — deterministic, hashed, manifest-first

The release skill bundles a curated subset of .claude/ — skills, agents, hooks, rules, the shared eval-gate — into a versioned, deterministic tar.gz. The safety filter drops secrets, .env files, .git/, runtime caches, and session state unconditionally: no flag re-admits them. Each bundle ships with a MANIFEST.json (per-file SHA-256), an INSTALL.md, and multiplatform installers so the recipient runs once and is done.

Preview the bundle — no tarball written

/cleanmatic:release -m pack --manifest .claude/pack.manifest.yaml --dry-run
release -m pack --manifest .claude/pack.manifest.yaml --dry-run --compute-sha

Build the real bundle

/cleanmatic:release -m pack --manifest .claude/pack.manifest.yaml

Output lands in dist/product-spec-{version}.tar.gz + a .sha256 sidecar. The dist/ directory is gitignored — tarballs are reproducible artifacts, not source. Same inputs always produce byte-identical output.

⚖️ Honest limit
  • No remote upload — use gh release upload or your CI pipeline after the tarball is built.
  • No GPG signing in v1 — SHA-256 sidecar only.
  • Determinism is a contract: SOURCE_DATE_EPOCH pins the timestamp; without it, mtime varies. CI builds should always set it.
STAGE 05

Observe — usage & health, never market effectiveness

After running the harness for a while, telemetry tells you — in plain Vietnamese — how the tooling is actually performing. Eight lenses cover skill invocation counts, script error rates, sub-agent success/fail, last validate result, and memory tidiness. A script gathers deterministic counts; the skill narrates them and always ends with a "what this does not measure" section. On a thin or new repo, most lenses say "chưa đủ dữ liệu" and suppress recommendations rather than inventing trends.

/cleanmatic:telemetry
telemetry --lens all --format ascii

Eight lenses

usage session health reliability workflow validate memory forensics

Four output formats

ascii md mermaid json
⚖️ Honest limit
  • Telemetry measures whether the machinery runs, not whether the product wins in the market. The validate proxy means "spec is well-formed" — not "users adopted it".
  • Token weight and duration figures are directional approximations, labelled "ước lượng" — not billing-exact.
  • Telemetry is read-only — it never edits specs, code, the catalog, or memory, and has no --apply.
THE RETURN EDGE

The return edge — critique back into decisions, --learn closes the loop

The pipeline is not linear — it has two explicit return paths that close the loop and make the harness self-improving over time.

Critique → recorded decisions via --apply-critique

After a critique report is generated, the PO reviews the findings. Accepted findings become DEC-<n> entries in the Decision Register — so they are not re-litigated in future critique runs and guide the next iteration of the spec. Run --apply-critique <report> to feed a report back into the spec workflow.

/cleanmatic:product-spec --apply-critique <path-to-critique-report>

--learn — spec → build → measure → learn

--learn closes the outermost ring. After a feature is built and measured, --learn takes outcome notes (what was observed post-build) and propagates them back into the spec's learning views — so the spec captures not just what was intended but what was learned. This feeds the --viz learning and --viz outcome-trend views.

/cleanmatic:product-spec --learn
🔄
The full loop in one line: product-spec defines and validates → product-spec-critique challenges → --apply-critique records decisions → the build team builds → --learn feeds outcomes back → telemetry reads health — and the next spec iteration starts better than the last.
