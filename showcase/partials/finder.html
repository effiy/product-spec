Skill finder

match the goal

Match the goal, not the name. The four skills each own a distinct job — they overlap at the edges. Scan the "if you want to…" tables to land on the right one, then use the tie-breaker rules when two skills both seem to fit. Still unsure? The last section points you to worked examples.

Pick by what you want

Four goal clusters — one per skill. Each cluster names the concrete things that skill handles. The pills show who it is designed for.

/cleanmatic:product-spec Product Owner

Define, structure, and govern a product spec. Use this when you are building or evolving the spec itself — from first interview to approved story.

  • Start a product from scratch (Vision → BRD → PRD → Epic → Story)
  • Add a new feature area (--prd), epic (--epic), or story (--story)
  • Decompose a brain-dump into a structured spec (--auto)
  • Seed the spec from raw transcripts or notes (--discover)
  • Run the structural + LLM validation gate (--validate)
  • Sign off an artifact (--approve) or log a ruling (--decision)
  • Update the spec without losing prior decisions (--update)
  • Produce a 1-page exec brief or release-notes delta (--summary)
  • Visualize the spec tree, roadmap, board, or MoSCoW coverage (--viz)
  • Act on a critique report finding-by-finding (--apply-critique)
  • Record real outcomes vs BRD goals after launch (--learn)

/cleanmatic:product-spec-critique Product Owner

Get an honest, opinionated tear-down of an existing spec. Use this after the spec exists and you want to know whether it is any good — not just structurally sound.

  • Find out why a spec would fail in the market (market lens)
  • Catch features nobody needs, fake personas, solution-first thinking (product lens)
  • Find untestable AC, non-INVEST stories, hidden dependencies (tech lens)
  • Audit writing quality — vague adjectives, term drift, wall-of-text (craft lens)
  • Pre-stakeholder gut-check on a PRD, epic, or story by ID
  • Tune the voice from gentle coaching to brutal honesty (--level 1..9)
  • Re-run cheaply after a fix — reuses prior lens work when the spec is unchanged

/cleanmatic:release Developer

Pack and ship the harness bundle. Use this when you need to share the .claude/ rig with another repo or cut an official versioned release.

  • Bundle a curated subset of .claude/ into a deterministic, versioned tar.gz
  • Preview the file list and size before building (--dry-run)
  • Build from an existing manifest (--manifest) or compose one interactively
  • Lock the CHANGELOG, bump the version, and hand off the tag-push for CI (release.py)
  • Seed a teammate's repo from this repo's working .claude/ setup

/cleanmatic:telemetry Product Owner

Read how your tooling is actually running — in plain Vietnamese. Use this after you have been using the harness for a while and want an honest usage + health read. It never writes anything.

  • See which skills get used and which are never touched (--lens usage)
  • Find scripts that error or run slow (--lens health)
  • Check subagent success / failure rates (--lens reliability)
  • See if the last --validate passed — as an internal quality proxy (--lens validate)
  • Audit memory tidiness — orphans, dead links, staleness (--lens memory)
  • Reconstruct a single session's full activity (--lens forensics --session <id>)
  • Get the full dashboard in one run (--lens all, the default)

Tie-breakers

When two skills seem to overlap, these rules settle it. They reflect the design intent documented in the SKILL.md files.

  • Define vs critique: No spec yet, or you are still building it → product-spec. Spec already exists and you want to know if it is any good → product-spec-critique. Critique is a consumer — it reads what product-spec wrote; it can't run without an existing spec.
  • Validate vs critique: Want a deterministic pass/fail on structure → product-spec --validate (the CI gate). Want an opinionated read on whether it is worth building → product-spec-critique (never a CI gate; non-deterministic by design).
  • Act on critique vs just read it: You have a critique report and want to record decisions from it → product-spec --apply-critique <report>. You just want the tear-down → product-spec-critique.
  • Ship a bundle vs observe usage: Need to package and distribute the .claude/ rig → release (developer, writes a tarball). Need to read how the rig is being used on a machine → telemetry (PO, read-only, no writes).
  • Telemetry validate lens vs product-spec --validate: --lens validate in telemetry is a proxy — it reads whether the last validate run passed. Run product-spec --validate to actually validate the spec now. They are different actions: observe vs execute.
  • record outcome vs observe health: Want to record a PO-declared outcome (target vs actual for a BRD goal) → product-spec --learn. Want to read the internal quality proxy of whether validate passed → telemetry --lens validate. The former writes; the latter reads.
  • release (cut) vs release (observe): Cutting a versioned release of the bundle → release. Observing how the installed skills are being used on someone's machine → telemetry. No overlap: one is the build tool, one is the usage reader.

What none of them do

Scope boundaries that apply across all four skills — not skill-by-skill gaps, but design constraints of the whole harness.

  • No production code. The harness specifies, critiques, packs, and observes — it never writes application code. That is the build team's job.
  • No autonomous scope decisions. Scope (in / out / core-value) is always the PO's call. The harness flags, surfaces, and asks — it never assumes scope. (GATE-NEVER-ASSUME.)
  • No silent reversals of approved content. Any contradiction with an approved artifact is a stop point — surfaced verbatim with Keep · Change · Hybrid choices. Never auto-fixed. (GATE-NO-SILENT-REVERSAL.)
  • No market-effectiveness measurement. Telemetry measures machinery health, not market outcomes. Even --learn in product-spec records PO-declared outcomes offline — it is not a market analytics tool.
  • No network calls at runtime. After install, all four skills run offline. (One caveat: if Mermaid failed to vendor at install time, product-spec's graph views fall back to a CDN script at browser-render — re-run the installer to vendor it.)
